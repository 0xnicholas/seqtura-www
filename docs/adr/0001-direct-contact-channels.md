# 0001 直接联系渠道取代预约表单

- Status: Accepted
- Date: 2026-11-16

## Context

官网原先以 `/contact` 的预约表单作为唯一转化入口：访客填写姓名、公司、邮箱与需求，服务端校验后通过飞书机器人 + SMTP 双路投递。表单是站点唯一的动态路由，需要维护校验、蜜罐、限流、投递与失败兜底；隐私政策也围绕表单字段、同意勾选与版本号编写。

站点上线前，业务侧决定取消预约表单，改为让客户直接通过企业微信、飞书或邮箱联系。同时去掉「30 分钟」的时长承诺——它没有实际约束力，也不应作为对外承诺。

## Decision

- 删除预约表单、`POST /api/contact`、`src/contact/**` 与邮件 / 飞书投递链路。
- `/contact` 改为「直接联系」页：企业微信二维码、飞书链接、邮箱。
- 全站主 CTA 统一为「预约沟通」，落点 `/contact#channels`。
- 不再承诺「30 分钟」；合作流程的初次沟通记为「1 次」。
- 隐私政策改为描述通过上述渠道主动提供的信息；保留 12 个月保存期限与权利条款。
- 保留 `server.mjs`、Node adapter 与安全头，站点不再有动态路由。

## Consequences

- 线索只存在于企业微信、飞书与邮箱的原生会话中，没有结构化的服务端记录或自动通知；渠道负责人需要自行跟进。
- 维护面缩小：不再有表单校验、限流、投递失败兜底与 SMTP / 飞书 webhook 配置；`nodemailer`、`zod` 等依赖可移除。
- 企业微信二维码必须是站内图片（CSP `img-src 'self'`）；飞书入口必须是可公开访问的链接。
- 隐私政策不再需要表单同意勾选、提交时间与隐私版本 payload；但企业微信（腾讯）与飞书（字节跳动）作为处理者需要披露。
- 如果未来重新引入表单，需要同时恢复服务端端点、限流、投递与同意机制。

## Alternatives considered

- 保留表单并只增加直连渠道：维护两套入口，隐私与投递链路继续存在，未采用。
- 只把表单换成第三方表单 / 日历：仍需要外部依赖与跨域配置，未采用。
- 保留「30 分钟」承诺：无法验证且不是实际约束，未采用。
